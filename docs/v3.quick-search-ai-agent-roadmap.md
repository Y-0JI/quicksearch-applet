# Quick Search — AI Agent Roadmap

## Status
Roadmap lanjutan setelah Phase 7 final verification.

## Tujuan Besar
Mengembangkan Quick Search dari universal launcher + conversational AI menjadi **controlled computer-aware AI agent** yang tetap ringan, aman, dan modular.

Agent harus dapat:

- memahami percakapan dan tujuan user;
- memilih tool yang tersedia;
- mencari file dan informasi web;
- melihat layar komputer saat diperlukan;
- membuka dan mengontrol aplikasi melalui tool terstruktur;
- menjalankan beberapa langkah secara berurutan;
- berhenti atau meminta konfirmasi untuk tindakan berisiko.

## Prinsip Arsitektur

```text
Quick Search
├── SEARCH
│   └── SearchEngine
│       ├── Apps
│       ├── Files
│       ├── Web
│       ├── URL
│       └── Calculator
│
└── ASK AI
    └── ConversationManager
        └── AgentManager
            └── AIManager
                └── AIProvider
                    └── 9Router / OpenRouter / OpenAI / Custom
                        
            ToolRegistry
            ├── File Tools
            ├── Web Tools
            ├── Screen Tool
            ├── App Tools
            └── Input/GUI Tools
```

### Tanggung jawab layer

**ConversationManager**
- Mengelola history user/assistant.
- Context limit.
- Session-only conversation.

**AIManager**
- Memilih provider.
- Menggabungkan konfigurasi.
- Menjadi satu-satunya entry point menuju AI provider.

**AIProvider**
- Komunikasi HTTP/model.
- Tidak menjalankan tool.
- Tidak mengetahui detail UI atau agent orchestration.

**AgentManager**
- Mengorkestrasi AI + tools.
- Menjalankan loop tool-call → tool-result → AI.
- Menangani step limit, cancellation, stale run, dan final answer.

**ToolRegistry**
- Menyimpan tool yang tersedia.
- Validasi tool dan argumen.
- Menjalankan tool melalui interface yang seragam.
- Menegakkan risk/permission policy.

**Tool**
- Satu kemampuan spesifik.
- Input schema jelas.
- Tidak memiliki akses di luar kemampuan yang didefinisikan.

# Phase 8 — Tool System / Tool Registry

## Objective
Membuat fondasi tool system tanpa mengubah AI conversation yang sudah stabil.

## Scope
Buat interface tool sederhana:

```text
Tool
├── id
├── name
├── description
├── inputSchema
├── riskLevel
└── execute(args, context, callback)
```

Buat `ToolRegistry` dengan kemampuan:

- register(tool)
- get(id)
- list()
- validate(id, args)
- execute(id, args, context, callback)
- cancel active execution bila tool mendukung cancellation

## Tool awal

1. `calculator`
2. `search_files`
3. `search_web`
4. `open_url`
5. `open_file`
6. `launch_app`

Reuse provider/logic existing sebanyak mungkin; jangan menduplikasi SearchEngine.

## Security

- Tool harus whitelist.
- Input tervalidasi sebelum execute.
- Tidak ada shell command dari model.
- Tidak ada arbitrary executable.
- Tidak ada shell string concatenation.
- Tool error dinormalisasi.

## Tests

- register/get/list
- unknown tool
- invalid arguments
- successful execution
- tool failure
- cancellation
- risk metadata

# Phase 9 — Agent Loop / AgentManager

## Objective
Mengubah ASK AI dari one-shot response menjadi tool-capable agent loop.

## Flow

```text
User
  ↓
AgentManager
  ↓
AIManager
  ↓
AI response
  ├── final answer → selesai
  └── tool call
        ↓
     ToolRegistry
        ↓
     tool result
        ↓
     AIManager
        ↓
     lanjut / final answer
```

## Behavior

- Agent mengirim available tool definitions ke model.
- Model boleh menghasilkan final answer atau tool request.
- Agent memvalidasi request sebelum execution.
- Hasil tool dimasukkan ke context.
- Agent memanggil model kembali.
- Loop dibatasi step count.

Default:

```text
maxAgentSteps = 8
```

## Cancellation

Satu agent run harus memiliki lifecycle sendiri:

```text
start
→ active
→ tool/AI calls
→ complete | cancelled | failed
```

Cancellation harus membatalkan seluruh run dan mencegah stale callback merender ke UI.

## Guardrails

- Tidak ada automatic retry.
- Unknown tool → error terkontrol.
- Invalid arguments → error terkontrol.
- Step limit → berhenti dengan status yang jelas.

## Tests

- no-tool final answer
- one-tool task
- multi-tool task
- unknown tool
- invalid arguments
- tool failure
- cancellation
- stale response
- max-step reached

**Stop dan review sebelum Phase 10.**

# Phase 10 — Screen Awareness / Vision Tool

## Objective
Membuat agent dapat melihat layar komputer saat diminta.

## Tool

`get_screen`

## Flow

```text
User
→ get_screen
→ screenshot
→ vision-capable model
→ analysis
→ answer / next tool
```

## Rules

- Screenshot hanya diambil on-demand.
- Tidak ada continuous capture default.
- Tidak disimpan permanen.
- Jangan menulis screenshot ke log.
- Jika model aktif tidak mendukung vision, return:

```text
vision-not-supported
```

- UI tetap responsive.

## Vision compatibility

Jangan mengasumsikan seluruh provider/model mendukung image input. Capability harus terdeteksi atau ditentukan oleh registry/provider metadata.

## Tests

- screenshot success
- no display/session
- vision unsupported
- image size handling
- cancellation
- no secret/image leakage to logs

**Stop dan review sebelum Phase 11.**

# Phase 11 — Structured Computer Control

## Objective
Memberi agent kemampuan mengontrol aplikasi secara terstruktur, bukan melalui shell bebas.

## Tools awal

1. `launch_app`
2. `focus_app`
3. `open_url`
4. `open_file`
5. `type_text`
6. `press_key`
7. `click`
8. `scroll`
9. `get_screen`

## Computer-use loop

```text
get_screen
  ↓
AI memahami layar
  ↓
action tool
  ↓
get_screen
  ↓
AI mengevaluasi perubahan
  ↓
lanjut / selesai
```

## Rules

- Mouse/keyboard action melalui native/system-safe mechanism yang tersedia.
- Tidak ada arbitrary shell execution.
- Coordinate input harus tervalidasi.
- Key input harus whitelist key names.
- Tidak ada system-wide mutation tanpa permission layer.
- Tool execution tetap asynchronous.

## Examples

```text
"Buka Chrome dan buka Google."
→ launch_app
→ open_url
```

```text
"Lihat layar saya dan klik tombol yang bertuliskan Login."
→ get_screen
→ model memilih target
→ click
→ get_screen
```

**Stop dan review sebelum Phase 12.**

# Phase 12 — Permission / Safety Model

## Objective
Membuat computer control aman dan dapat diprediksi.

## Risk levels

### LOW
- get_screen
- search_files
- search_web
- calculator
- open_url
- focus_app

### MEDIUM
- launch_app
- open_file
- type_text
- press_key
- click
- scroll

### HIGH
- delete file
- move/rename file
- install software
- system configuration
- arbitrary command execution

## Rules

LOW
→ execute otomatis.

MEDIUM
→ default dapat dieksekusi sesuai policy/settings.

HIGH
→ wajib meminta konfirmasi user.

Contoh:

```text
AI:
Saya menemukan file ~/Documents/test.txt.
Apakah Anda ingin menghapusnya?

[ Batal ] [ Izinkan ]
```

## Requirements

- Tool risk level diketahui sebelum execute.
- UI menampilkan tindakan yang akan dilakukan.
- User dapat deny.
- Deny tidak merusak conversation.
- Cancellation tetap tersedia.
- Agent tidak boleh menyamarkan tindakan berisiko.

## Hard security rule

Jangan pernah memberikan agent akses langsung ke:

- shell bebas
- `bash -c`
- arbitrary `exec`
- `sudo`
- system package installation tanpa approval
- arbitrary filesystem mutation

# Phase 13 — Agent UX / UI Integration

## Objective
Membuat agent terasa natural tanpa mengubah Quick Search menjadi UI yang berat.

## UI state

```text
User question
↓
Thinking...
↓
Working: Searching files...
↓
Working: Looking at screen...
↓
Working: Opening application...
↓
AI final answer
```

Tool activity ditampilkan sebagai status ringan, bukan full chat bubble kecuali diperlukan untuk audit pengguna.

Contoh:

```text
[ Searching files... ]
[ Looking at screen... ]
[ Opening Chrome... ]
[ Done ]
```

## Requirements

- Follow-up input existing tetap dipakai.
- Conversation tetap scrollable.
- Tool activity tidak memenuhi history conversation.
- Error tool tampil dengan bahasa natural.
- Confirmation dialog mengikuti risk policy.
- Agent cancellation terlihat jelas dan tidak meninggalkan stale UI.

# Execution Rules untuk Agent

Kerjakan satu phase per satu.

Untuk setiap phase:

1. inspeksi kode existing;
2. tulis rencana implementasi sebelum mengubah kode;
3. implement solusi paling sederhana yang konsisten dengan arsitektur existing;
4. unit test;
5. runtime verification di Cinnamon;
6. review diff;
7. commit + push;
8. BERHENTI untuk review.

Jangan melompati phase.

Jangan mengubah SEARCH behavior yang sudah stabil kecuali regression mengharuskan fix.

Jangan menambahkan feature di luar phase aktif.

Prioritas keputusan:

```text
Security
↓
Stability
↓
Correctness
↓
Maintainability
↓
UX
↓
Feature breadth
```

# Target Akhir

Quick Search menjadi:

> Universal launcher + conversational AI + controlled computer-aware agent.

Agent dapat memahami tujuan user, memilih tool, melihat layar, mencari file/web, membuka aplikasi, melakukan tindakan GUI secara terstruktur, menjalankan beberapa langkah, dan meminta konfirmasi untuk tindakan berisiko — tanpa memberikan akses shell bebas kepada model.
